## Cara pakai

- Ini adalah **4 prompt terpisah**, satu per tahap roadmap: Step 0 (gerbang), Tahap Now/Tier D, Tahap Next/Tier F, Tahap Later.
- Jalankan **satu per satu, berurutan**, di sesi Replit AI (Agent atau Chat). Jangan tempel semuanya sekaligus.
- **Jangan mulai Prompt 2 sebelum Prompt 1 selesai dan diverifikasi.** Setiap prompt punya bagian "Bukti yang wajib ditunjukkan" — jangan lanjut ke tahap berikutnya sampai bukti itu benar-benar ada (output terminal asli, bukan klaim).

=== SPESIFIKASI TEKNIS PERSIS (jangan diubah tanpa konfirmasi saya) ===

STACK: Sui Move (contract) + TypeScript/React (web) + Node.js (API).
Deployment: Sui TESTNET saja.

--- Model objek Move (konsep, sesuaikan syntax dengan toolchain nyata) ---

AgentAccount:
  id, owner/capability, status (ACTIVE|REVOKED), policy_version,
  per_tx_limit, daily_limit, spent_today, day_bucket, last_nonce

Service:
  id, service_id, recipient, asset_type, price, metadata_uri, active

PaymentIntent:
  intent_id (UUID v4, unik global — dicek via lookup on-chain untuk cegah
    settle dua kali), agent_account_id, service_id, recipient, amount,
    asset_type, reason_hash (sha256 dari reason plaintext — reason
    plaintext-nya TIDAK disimpan on-chain, hanya di API layer), expires_at,
    nonce (counter sekuensial per-account, harus == AgentAccount.last_nonce
    + 1 — ini BEDA dari intent_id, dua-duanya wajib ada dan tidak boleh
    disatukan)

PaymentReceipt:
  id, intent_id, service_id, amount, recipient, settled_at,
  artifact_uri (opsional, boleh dikosongkan di Tier D)

--- Aturan day_bucket (WAJIB, jangan diubah logikanya) ---

day_bucket dihitung on-chain dari Sui shared Clock object:
  day_bucket = Clock.timestamp_ms() / 86_400_000
Ini adalah window UTC TETAP (fixed), BUKAN rolling 24 jam. spent_today
direset ke 0 saat transaksi pertama diproses pada day_bucket baru. JANGAN
memakai timestamp dari client atau wall-clock off-chain untuk ini — HARUS
pakai Clock shared object Sui. Dokumentasikan di threat-model.md bahwa ada
edge case di sekitar batas UTC (dua transaksi terpisah ~1 menit yang
melintasi tengah malam UTC bisa lolos dua kali limit harian) — ini
simplifikasi yang disengaja, bukan bug yang harus diperbaiki di Tier D.

--- Invariant Move yang WAJIB dites (positive DAN negative test untuk
    setiap satu, jangan hanya positive) ---

- hanya owner/capability berwenang yang bisa mengubah policy
- akun revoked tidak bisa settle
- intent kedaluwarsa tidak bisa settle
- pembayaran tidak boleh melebihi per_tx_limit
- total harian tidak boleh melebihi daily_limit (dites termasuk kasus
  batas UTC di atas)
- recipient harus cocok dengan service yang terdaftar
- intent_id yang sama tidak bisa settle dua kali
- nonce harus sekuensial (nonce != last_nonce + 1 harus gagal)
- jumlah di receipt harus sama persis dengan jumlah yang settle
- policy check yang gagal TIDAK BOLEH mengubah spent_today
- semua jalur settlement sukses memancarkan event kanonik yang sama

--- Error taxonomy PERSIS ini, jangan tambah/kurang tanpa konfirmasi ---

E_ACCOUNT_NOT_ACTIVE
E_POLICY_EXPIRED
E_TX_LIMIT_EXCEEDED
E_DAILY_LIMIT_EXCEEDED
E_SERVICE_NOT_FOUND
E_SERVICE_INACTIVE
E_RECIPIENT_MISMATCH
E_INTENT_EXPIRED

E_NONCE_OUT_OF_ORDER
E_UNSUPPORTED_ASSET
E_UNAUTHORIZED_OWNER
E_INSUFFICIENT_BALANCE
E_NETWORK_MISMATCH

--- Kontrak API PERSIS ini (field names harus sama persis) ---

POST /api/intents/prepare
Request:
{
  "agentAccountId": "0x...",
  "userRequest": "teks natural language dari user",
  "serviceId": "id-layanan-terdaftar"
}
Response:
{
  "intentId": "string",
  "status": "POLICY_CHECKED",
  "serviceId": "string",
  "recipient": "0x...",
  "amount": "string (dalam unit terkecil)",
  "asset": "SUI",
  "reason": "teks plaintext yang bisa dibaca manusia",
  "reasonHash": "sha256:...",
  "nonce": number,
  "policyDecision": {
    "allowed": boolean,
    "requiresApproval": boolean,
    "reasons": []
  },
  "expiresAt": "ISO8601"
}

POST /api/intents/:intentId/execute
- Server WAJIB re-validasi ulang semua field kritis, TIDAK BOLEH percaya
  amount/recipient dari client.
- Server WAJIB verifikasi sha256(reason) === reasonHash sebelum
  menampilkan reason ke UI sebagai teks tepercaya. Jika tidak cocok,
  tampilkan status "integrity mismatch", JANGAN tampilkan reason-nya.
- Response harus berisi: transaction digest, receipt ID, status akhir.

--- UI wajib menampilkan reason PLAINTEXT yang sudah diverifikasi hash-nya,
    bukan hash mentah, ke pengguna sebelum eksekusi. ---

=== DAFTAR KERJA TIER D (urutkan persis seperti ini, satu per satu) ===

1. Move package `contracts/agent_commerce`:
   a. Buat struct AgentAccount + fungsi create/revoke + emit event.
      Compile (`sui move build`), tempel output asli.
   b. Buat struct Policy fields (per_tx_limit, daily_limit, day_bucket
      pakai Clock) + fungsi update policy oleh owner saja. Tulis unit
      test Move untuk unauthorized-mutation-must-fail. Jalankan
      `sui move test`, tempel output asli (termasuk kalau ada yang gagal).
   c. Buat struct Service + registry fungsi tambah/nonaktifkan service.
      Test: recipient tidak bisa di-override dari luar registry.
   d. Buat struct PaymentIntent + fungsi settle dengan SELURUH invariant
      di atas. Tulis unit test POSITIF dan NEGATIF untuk SETIAP invariant
      yang didaftar di atas — satu per satu, bukan digabung jadi satu test
      besar. Jalankan `sui move test`, tempel output lengkap.
   e. Buat struct PaymentReceipt + event emission.
   f. Publish ke testnet (`sui client publish`). Tempel output ASLI berisi
      package ID. Simpan package ID ini di file config terpusat, bukan
      hardcode.

2. `packages/domain`: schema TypeScript untuk Intent, Service,
   PolicyDecision — field names harus sama persis dengan kontrak API di
   atas. Gunakan validator schema (zod atau setara) sehingga semua output
   model AI divalidasi sebelum dipakai.

3. `packages/agent-core`: planner yang mengubah teks natural language jadi
   typed service request, PLUS provider AI mock deterministik yang bisa
   dipakai sebagai fallback. Uji bahwa mock dan live provider (jika API
   key tersedia) menghasilkan keputusan policy yang sama untuk skenario
   demo yang sama.

4. `apps/api`: implementasi endpoint `/api/intents/prepare` dan
   `/api/intents/:id/execute` persis sesuai kontrak di atas, termasuk
   verifikasi reason-hash dan revalidasi semua field kritis di server.

5. `apps/web`: UI minimal — connect wallet, buat agent account + policy,
   input request natural language, tampilan hasil simulasi
   (ALLOWED/APPROVAL_REQUIRED/REJECTED dengan daftar rule yang lolos/gagal),
   tombol eksekusi, tampilan digest + link explorer, activity feed
   sederhana. Simulator ini HARUS berdiri sendiri (bisa dites tanpa
   dashboard kebijakan penuh — dashboard penuh itu tugas Tier F).

6. Network-mismatch guard: app harus menolak render jika client config
   menunjuk ke network yang tidak sesuai (mis. mainnet RPC padahal
   seharusnya testnet). Tulis satu test untuk skenario ini.

7. Demo reliability:
   a. Script untuk pre-fund wallet demo dengan saldo testnet deterministik
      (`scripts/fund-demo-wallets.ts`) — jalankan dan tunjukkan hasil asli.
   b. Dua service seed di registry.
   c. Tiga skenario demo: (1) pembayaran diterima, (2) ditolak karena
      over-budget, (3) ditolak karena recipient tidak dikenal.
   d. Jalankan ketiga skenario ini di testnet SUNGGUHAN tiga kali
      berturut-turut, tempel output/digest asli setiap kali, dan ukur
      total waktu dari "wallet sudah terhubung" sampai "receipt tampil" —
      laporkan angka detik yang sebenarnya, bukan estimasi.

8. `docs/threat-model.md`: tulis batasan yang sudah diketahui (termasuk
   catatan batas UTC di atas), dan daftar apa yang TIDAK dijamin oleh
   sistem ini di Tier D.

=== SECURITY GATE TIER D — WAJIB LULUS SEMUA SEBELUM MENGANGGAP SELESAI ===

Contract gate:
- [ ] over-limit payment gagal (bukti test asli)
- [ ] daily-limit overflow gagal, termasuk kasus batas UTC (bukti test asli)
- [ ] unregistered service gagal (bukti test asli)
- [ ] recipient mismatch gagal (bukti test asli)
- [ ] expired intent gagal (bukti test asli)
- [ ] revoked account gagal (bukti test asli)
- [ ] duplicate intent_id gagal (bukti test asli)
- [ ] out-of-order nonce gagal (bukti test asli)
- [ ] failed transaction tidak mengubah saldo/accounting (bukti test asli)

Agent gate:
- [ ] agent tidak pernah memegang private key
- [ ] agent hanya memilih service yang terdaftar
- [ ] schema validation menolak output model yang malformed (bukti test)
- [ ] prompt-injection test tidak bisa memaksa recipient sembarangan

Application gate:
- [ ] frontend tidak pernah dipercaya untuk amount/recipient (server

- [ ] reason-hash diverifikasi di server sebelum ditampilkan (bukti test)
- [ ] tidak ada endpoint arbitrary-transfer
- [ ] network-mismatch guard aktif (bukti test)

Demo gate:
- [ ] testnet banner selalu terlihat
- [ ] wallet demo pre-funded, tidak bergantung pada faucet live saat demo
- [ ] mock AI fallback teruji setara dengan live provider
- [ ] skenario sukses berjalan 3x berturut-turut (bukti digest asli x3)
- [ ] tiap skenario penolakan berjalan 3x berturut-turut (bukti asli x3)
- [ ] total waktu demo end-to-end di bawah 3 menit (bukti angka asli)
